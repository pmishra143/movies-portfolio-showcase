How ranking works

The quality blend adapts a function from the private app. It combines an audience score, a critic score scaled to ten, and a capped vote-confidence contribution. Missing critic scores fall back to the audience score. 

score = audience × 0.55 + critic/10 × 0.35
      + min(2, sqrt(votes / 100000)) × 0.10

This heuristic is not a calibrated recommendation model, and the displayed rating is the audience fixture score, not the blend.

01 / SOURCE BOUNDARY

Related to real work. Honest about scope.

The private app includes scheduled catalog ingestion, multi-source discovery, metadata enrichment, cached catalog serving and user preferences. This public edition reimplements a focused browsing experience using original fictional data. It does not call those private services.

The ranking formula is adapted from the original browser code. The static frontend, fixture pipeline and recovery exercise in this repo are newly written showcase components.

02 / DATA CONTRACT

Validate before publishing.

The reproducible pipeline checks schema, stable identity, uniqueness, dates, ratings and platform names. It produces a deterministic snapshot and a checksum manifest. Failed validation leaves the previous published artifact intact.

Fictional input→Contract checks→Atomic snapshot→Static serving
03 / FAILURE EXERCISE

Availability is not freshness.

Normal demo state: the bundled snapshot is available. Its date is explicit; no live-provider health is claimed.

Local UI simulation. It retains the loaded fixture and shows degraded status; it does not inject a fault into the private app.

04 / OPERATING PRACTICES

Evidence over uptime claims.

Unit tests cover filtering, ranking, validation and browser-storage failures. Pipeline tests cover rejected input and preservation of the last published snapshot. Browser checks exercise navigation, dialogs, saved lists, failure states and mobile layout.

This portfolio does not claim production throughput, uptime, MTTR improvements or Disney affiliation.
